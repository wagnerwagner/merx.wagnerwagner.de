Title: Stock management

----

Headline: 

----

Intro: Your granny knitted ten pairs of socks, so you can’t sell eleven. Merx caps the quantity per product itself; keeping the actual stock up to date is your part.

----

Text:

Merx already refuses to put more of a product into the cart than [`maxQuantity()`](/reference/classes/product-page/max-quantity) allows. Stock management is therefore two things: telling Merx what the limit is, and reducing it once an order has been paid. We will do both.

## Cap the quantity per product

Add a `maxQuantity` field to the product page and Merx enforces it on every [`add()`](/reference/classes/cart/add) and [`updateItem()`](/reference/classes/cart/update-item).

<code caption="/content/products/knitted-socks/product.txt">
```kirby
Title: Knitted socks

\----

Price: 14.99

\----

Maxquantity: 10
```
</code>

Going over the limit throws with [`error.merx.cart.maxQuantity`](/reference/options/translations/error-merx-cart-maxquantity), which reads *“There are only 10 of “Knitted socks” left.”* — so the API returns a usable message without any work on your side. A `maxQuantity` field on the site applies to every product that does not set its own.

## Drive the cap from your stock

A fixed `maxQuantity` does not shrink as you sell. Keep the real number in a `stock` field instead and let the cap follow it, by overriding [`maxQuantity()`](/reference/classes/product-page/max-quantity) in your own product model.

<code caption="/site/models/product.php">
```php
<?php

class ProductPage extends \Wagnerwagner\Merx\ProductPage
{
  public function maxQuantity(): ?float
  {
    return $this->stock()->isEmpty() ? null : $this->stock()->toFloat();
  }
}
```
</code>

Returning `null` means *no limit*, so products without a `stock` field stay unrestricted. With three pairs left, adding a fourth now fails with Merx’ own message.

## Check again at checkout

A cart lives in the customer’s session and can sit there for days while stock runs out elsewhere. Check once more before the payment starts, with the [`initializeOrder:before`](/reference/options/hooks/initialize-order-before) hook.

<code caption="/site/config/config.php">
```php
<?php

use Kirby\Exception\Exception;
use Wagnerwagner\Merx\Cart;
use Wagnerwagner\Merx\OrderPage;
use Wagnerwagner\Merx\ProductList;

function quantitiesPerProduct(ProductList $cart): array
{
  $quantities = [];

  foreach ($cart->filterByType('product') as $item) {
    // A product without a stock field is unlimited.
    if ($item->page?->stock()->isNotEmpty()) {
      $uuid = (string)$item->page->uuid();
      $quantities[$uuid] = ($quantities[$uuid] ?? 0) + $item->quantity;
    }
  }

  return $quantities;
}

function checkStock(ProductList $cart): void
{
  foreach (quantitiesPerProduct($cart) as $uuid => $quantity) {
    $page = page($uuid);

    if ($page->stock()->toFloat() < $quantity) {
      throw new Exception(
        key: 'stock.insufficient',
        httpCode: 400,
        fallback: 'Only {stock} of “{title}” left.',
        data: [
          'stock' => $page->stock()->toFloat(),
          'title' => (string)$page->title(),
        ],
      );
    }
  }
}

return [
  'hooks' => [
    'wagnerwagner.merx.initializeOrder:before' => function (Cart $cart, array $data): void {
      checkStock($cart);
    },
    'wagnerwagner.merx.createOrder:before' => function (OrderPage $virtualOrderPage, array $gateway, array $data): void {
      checkStock($virtualOrderPage->cart());
    },
  ],
];
```
</code>

`quantitiesPerProduct()` adds up the lines of each product first. A [personalized product](/cookbook/personalized-products) gets one line per name, and `maxQuantity()` checks every line on its own, so ten pairs for Anna and ten for Ben get past the cart and stop here.

[`createOrder:before`](/reference/options/hooks/create-order-before) is the second gate. It runs after the customer comes back from the payment provider, which is where the last of a product can disappear between two shoppers.

<callout>
[`$orderPage->cart()`](/reference/classes/order-page/cart) returns [`ListItem`](/reference/classes/list-item) objects, so the product is `$item->page` and the amount ordered is `$item->quantity`.
</callout>

## Reduce the stock once paid

The [`orderPaid`](/reference/options/hooks/order-paid) hook fires exactly once, when the order becomes paid. That also covers payment methods which confirm hours later through a [Stripe webhook](/guide/configuration/stripe-webhooks), so it’s the only place you have to write.

Writing to a page needs permissions the customer does not have, so wrap the update in [`impersonate()`](https://getkirby.com/docs/reference/objects/cms/app/impersonate).

<code caption="/site/config/config.php">
```php
'wagnerwagner.merx.orderPaid' => function (OrderPage $orderPage): void {
  kirby()->impersonate('kirby', function () use ($orderPage): void {
    foreach (quantitiesPerProduct($orderPage->cart()) as $uuid => $quantity) {
      $page = page($uuid);
      $page->update([
        'stock' => $page->stock()->toFloat() - $quantity,
      ]);
    }
  });
},
```
</code>

Update every product once, on a page you have just looked up. [`update()`](https://getkirby.com/docs/guide/templates/php-api#immutable-objects) leaves the old object behind, and updating that one again throws and removes the page’s content from disk.

## Show the message

The checkout form posts to [`/api/shop/checkout`](/reference/api/routes/shop-checkout-post), so the exception never reaches a controller — it comes back as JSON, with the status code you threw it with.

<code caption="Response">
```json
{
  "status": "error",
  "code": 400,
  "key": "error.stock.insufficient",
  "message": "Only 3 of “Knitted socks” left."
}
```
</code>

Note the prefix: the `stock.insufficient` you threw arrives as `error.stock.insufficient`.

The checkout JavaScript in [Validate checkout](/guide/getting-started/validate-checkout) already handles it. Anything whose key is not `error.merx.fieldsvalidation` is shown as a general message above the submit button — which is where a stock error belongs, since it is about the cart rather than one field.

<callout>
Reserving stock while a payment is in flight is a different problem, and one Merx does not solve for you. If you sell single items, consider unpublishing the product in `createOrder:before` and publishing it again if the payment fails.
</callout>
