Title: Upgrade Merx 1 to 2

----

Headline: 

----

Intro: What changed between Merx 1 and Merx 2, and what you have to rewrite.

----

Text:

Merx 2 renames a lot and moves a few things to a different place entirely. Work through the sections below in order; each one is independent.

## Page models

The abstract model is gone. Extend the class instead.

```php title="/site/models/order.php (Merx 1)"
class OrderPage extends OrderPageAbstract
{
}
```

```php title="/site/models/order.php (Merx 2)"
class OrderPage extends \Wagnerwagner\Merx\OrderPage
{
}
```

Merx 2 brings a model for products as well. If you have a `/site/models/product.php`, let it extend [`\Wagnerwagner\Merx\ProductPage`](/reference/classes/product-page) instead of `Page`, or `price()`, `stock()` and `tax()` are missing.

Delete a `/site/models/orders.php` of your own. It replaces the model Merx registers for the orders page, which keeps the list of all orders, and with it their secret URLs, out of `$site->index()`.

## Options

Every option moved namespace.

`ww.merx.[name]` → [`wagnerwagner.merx.[name]`](/reference/options)

Some are gone.

- `currency` is replaced by [pricing rules](/guide/configuration/currencies), which set the currency per rule instead of once for the whole shop.
- `currencySymbol`, `currencyPositionPrecedes`, `currencySeparateBySpace`, `currencyDecimalPoint` and `currencyThousandsSeparator` are replaced by the locale, which formats every price, see [Number formatting](/guide/configuration/localization#number-formatting).
- `cart.fields` is gone: every item keeps its page, so read the fields from `$item->page`.
- `successPage` is replaced by the [API](/guide/api/concept) — see *The success page* below.

`stripe.webhook_signing_secret` is split into [`stripe.test.webhook_signing_secret`](/reference/options/config-options/stripe-test-webhook-signing-secret) and [`stripe.live.webhook_signing_secret`](/reference/options/config-options/stripe-live-webhook-signing-secret), like the keys.

Everything else is new. The [config options reference](/reference/options/config-options) lists them all.

[`license`](/reference/options/config-options/license) keeps its name, but a Merx 1 license key is not valid for Merx 2: the Panel shows it as invalid. A shop that takes real orders needs a Merx 2 [license](/license).

## Products

A product carried its tax rate as a percentage. It now names a tax rule, and the rate lives in the config.

```kirby title="/content/products/1_bike/product.txt (Merx 1)"
Price: 2000

\----

Tax: 19
```

```kirby title="/content/products/1_bike/product.txt (Merx 2)"
Price: 2000

\----

Taxrule: default
```

The rule itself goes into [`taxRules`](/reference/options/config-options/tax-rules), with the rate as a decimal: `Tax: 19` becomes `'rate' => 0.19`. See [Taxes](/guide/configuration/taxes).

Merx counts the [stock](/guide/getting-started/stock) itself. A `Stock` field keeps working as it is, but delete the hooks that lowered it, or every order lowers it twice. The method returns the number now, not the field:

`$page->stock()->toFloat()` → [`$page->stock()`](/reference/classes/product-page/stock)

`price()` and `tax()` return objects, too. `$page->price()` is a [`Price`](/reference/classes/price). `$page->tax()` is the tax **amount** as a [`Tax`](/reference/classes/tax), not the rate any more: for “incl. 19 % VAT”, use `$page->tax()?->rate()`.

## Hooks

`initializePayment:before` → [`initializeOrder:before`](/reference/options/hooks/initialize-order-before)
`initializePayment:after` → [`initializeOrder:after`](/reference/options/hooks/initialize-order-after)
`completePayment:before` → [`createOrder:before`](/reference/options/hooks/create-order-before)
`completePayment:after` → [`createOrder:after`](/reference/options/hooks/create-order-after)

`initializeOrder:after` gets the order as `$orderPage`, not as `$virtualOrderPage`: it is saved as a draft by then. Kirby passes hook arguments by name, so rename the parameter.

The single `ww.merx.cart` hook is gone. It fired whenever a cart was built; there is now one pair of hooks per operation.

`cart` → [`cart.add:after`](/reference/options/hooks/cart-add-after), [`cart.remove:after`](/reference/options/hooks/cart-remove-after) and [`cart.updateItem:after`](/reference/options/hooks/cart-update-item-after)

These run when the cart changes. Code that has to run whenever a cart is built, like the old hook, goes into [`cart.create:after`](/reference/options/hooks/cart-create-after).

Apart from that, there are many more [new hooks](/reference/options/hooks).

## Merx methods

`Merx::initializePayment` → [`Merx::initializeOrder`](/reference/classes/merx/initialize-order)
`Merx::completePayment` → [`Merx::createOrder`](/reference/classes/merx/create-order)
`Merx::formatPrice` → [`Merx::formatCurrency`](/reference/classes/merx/format-currency)
`Merx::getMessage` → [`Merx::error`](/reference/classes/merx/error)

[`error()`](/reference/classes/merx/error) returns why a payment could not be completed, as an array with the translation `key` and the `message`. Merx sets it itself: the [success route](/reference/api/routes/shop-success-get) stores the error before it sends the customer back to the checkout page. To set a message of your own in place of `Merx::setMessage`, write to the same session key.

```php
kirby()->session()->set(Merx::$errorSessionKey, [
  'key' => null,
  'message' => 'Your message',
]);
```

`Merx::calculateNet` and `Merx::getFieldError` are gone without a replacement. Net prices are part of [`Price`](/reference/classes/price) now, and field errors come back from the [checkout endpoint](/reference/api/routes/shop-checkout-post) as JSON.

The global functions are gone, apart from `merx()` and `cart()`.

`formatPrice()` → [`Merx::formatCurrency()`](/reference/classes/merx/format-currency)
`formatIBAN()` → [`Merx::formatIBAN()`](/reference/classes/merx/format-i-b-a-n)
`calculateTax()` → [`Merx::calculateTax()`](/reference/classes/merx/calculate-tax), with the rate as a decimal
`productList()` → [`new ProductList()`](/reference/classes/product-list)

`formatCurrency` takes a currency, where `formatPrice` used the global option. You can wrap it.

```php title="/site/config/config.php"
<?php

use Wagnerwagner\Merx\Merx;

if (!function_exists('formatPrice')) {
  function formatPrice(float $price): string {
    return Merx::formatCurrency($price, 'EUR');
  }
}
```

## Cart and items

`$cart->append()` → [`$cart->add()`](/reference/classes/cart/add)
`$cart->update([…])` → [`$cart->updateItem($key, […])`](/reference/classes/cart/update-item), one item at a time
`$cart->getSum()` → [`$cart->total()`](/reference/classes/cart/total)
`$cart->getTax()` → `$cart->total()->tax`
`$cart->getTaxRates()` → [`$cart->taxRates()`](/reference/classes/cart/tax-rates)

`getFormattedItems()` is gone. Items format themselves — see *Reading cart items* below.

The cart is stored under a different session key, so carts that visitors filled before the upgrade are empty afterwards.

### Adding to the cart

`add()` took an `id` plus arbitrary keys at the top level. It now accepts the parameters of [`new ListItem()`](/reference/classes/list-item/__construct) and nothing else, so any other key fails with `Unknown named parameter`.

The identifier is `key` instead of `id`, the product page is `page`, and your own attributes belong in `data`. Leaving out `key` makes Merx use the page’s UUID.

Title and price of an item with a page are read from the page with every request. A `title` or `price` passed to `add()` no longer overrides them. Override `title()` or [`price()`](/reference/classes/product-page/price) in your product model instead.

```php title="Merx 1"
$cart->add([
  'id' => 'products/nice-shoes',
  'color' => 'red',
]);
```

```php title="Merx 2"
$cart->add([
  'key' => 'nice-shoes-red',
  'page' => 'products/nice-shoes',
  'data' => ['color' => 'red'],
]);
```

### Reading cart items

Cart items were arrays. They are [`ListItem`](/reference/classes/list-item) objects now, in the cart as well as in [`$orderPage->cart()`](/reference/classes/order-page/cart).

`$cartItem['id']` → `$item->page`
`$cartItem['quantity']` → `$item->quantity`
`$cartItem['price']` → `$item->price`

## Order page

`$orderPage->invoiceNumber()` → [`$orderPage->orderNumber()`](/reference/options/config-options/order-number)
`$orderPage->invoiceDate()` → `$orderPage->dateCreated()`
`$orderPage->payedDate()` and `paidDate()` → `$orderPage->datePaid()`
`$orderPage->paymentComplete()` → [`$orderPage->isPaid()`](/reference/classes/order-page/is-paid)
`$orderPage->formattedSum()` → [`$orderPage->total()`](/reference/classes/order-page/total)

The order number is stored on the page now. Merx 1 derived it from the page’s sorting number, so it changed when the order was re-sorted. You can replace how it is built with the [`orderNumber`](/reference/options/config-options/order-number) option.

## Existing orders

Merx does not migrate the orders you already have, and Merx 2 cannot read them as Merx 1 wrote them. This is what changed:

- `Invoicedate` → `Datecreated`, `Paymentmethod` → `Paymentgateway`
- `Paymentcomplete` is gone. An order is paid once it has a `Datepaid`, which was `Paiddate` (or `Payeddate` before Merx 1.7).
- The order number is a field now, `Ordernumber`. Without it an order stays untitled. Merx 1 showed the sorting number with five digits, `00042`.
- Every entry in `Items` needs a `type` — `product` for anything you sell, where Merx 1 wrote `template`. Its tax rate is `taxrate` as a decimal (`0.19`), not `taxRate` in percent (`19`), and it needs a `currency`.
- `Paymentdetails` held the provider’s whole response, including the customer’s personal data. Merx 2 keeps a short [record](/reference/classes/payment-details/create). Its `provider` is what the Panel links to the payment with.
- Merx 2 keeps an order in the default language only.

The script below does all of it. It writes the content files directly: an update through Kirby would run the hooks, and every paid order would send its “paid” email again. Back up `/content` first, set your currency, and run it once with `php migrate-orders.php`.

```php title="/migrate-orders.php"
<?php

use Kirby\Cms\App;
use Kirby\Data\Txt;
use Kirby\Data\Yaml;
use Kirby\Filesystem\F;
use Wagnerwagner\Merx\PaymentDetails;

require __DIR__ . '/kirby/bootstrap.php';

$kirby = new App();
$currency = 'EUR';
$language = $kirby->defaultLanguage()?->code();
$suffix = $language === null ? '.txt' : '.' . $language . '.txt';

foreach (glob($kirby->site()->ordersPage()->root() . '/*_*/order*.txt') as $file) {
	// Merx keeps an order in the default language only
	if (str_ends_with($file, $suffix) === false) {
		F::remove($file);
		continue;
	}

	$data = Txt::decode(F::read($file));
	if (isset($data['datecreated']) === true) {
		continue;
	}

	$isPaid = ($data['paymentcomplete'] ?? '') === 'true';
	$data['datecreated'] = $data['invoicedate'] ?? '';
	// Merx 1 wrote `Payeddate` up to version 1.6
	$datePaid = ($data['paiddate'] ?? '') ?: ($data['payeddate'] ?? '') ?: $data['datecreated'];
	$data['datepaid'] = $isPaid ? $datePaid : '';
	$data['paymentgateway'] = $data['paymentmethod'] ?? '';
	// What `invoiceNumber()` returned: the sorting number with five digits
	$data['ordernumber'] = str_pad(strtok(basename(dirname($file)), '_'), 5, '0', STR_PAD_LEFT);

	$data['items'] = Yaml::encode(array_map(fn (array $item): array => [
		// Long values were written as folded strings, which end with a line break
		'key' => trim($item['key']),
		'title' => $item['title'],
		'quantity' => (float)$item['quantity'],
		'type' => $item['template'] === 'shipping' ? 'shipping' : 'product',
		'price' => (float)$item['price'],
		'taxrate' => (float)$item['taxRate'] / 100,
		'currency' => $currency,
	], Yaml::decode($data['items'] ?? '')));

	// Merx 1 kept the provider’s whole response, with the customer’s personal data
	$details = Yaml::decode($data['paymentdetails'] ?? '');
	if (str_starts_with($details['id'] ?? '', 'pi_') === true) {
		$data['paymentdetails'] = Yaml::encode(PaymentDetails::create([
			'provider' => 'stripe',
			'id' => $details['id'],
			'status' => $details['status'] ?? null,
			'amount' => $details['amount'] / 100,
			'currency' => strtoupper($details['currency']),
			'created' => date('c', $details['created']),
			'livemode' => $details['livemode'] === true,
		]));
	} elseif (isset($details['purchase_units']) === true) {
		$data['paymentdetails'] = Yaml::encode(PaymentDetails::fromPayPalOrder($details));
	}

	unset($data['invoicedate'], $data['paiddate'], $data['payeddate'], $data['paymentcomplete'], $data['paymentmethod']);
	F::write($file, Txt::encode($data));
}
```

Merx 1’s payment method names, such as `credit-card-sca`, stay in `Paymentgateway` as a record. Merx 2 doesn’t look them up.

New orders count on from the last one. To keep the five digits, pad them in the [`orderNumber`](/reference/options/config-options/order-number) option, or `00042` is followed by `43`.

```php title="/site/config/config.php"
<?php

use Wagnerwagner\Merx\OrderPage;

return [
	'wagnerwagner.merx.orderNumber' => function (OrderPage $virtualOrderPage): string {
		$lastOrder = $virtualOrderPage->siblings()->listed()->last();
		return str_pad((string)(($lastOrder?->orderNumber()->toInt() ?? 0) + 1), 5, '0', STR_PAD_LEFT);
	},
];
```

## Blueprints

Kirby 6 replaced sections with fields, and so did Merx.

`sections/order` → [`fields/order`](/reference/blueprints/fields/order), a field group
`sections/orders` → [`fields/orders`](/reference/blueprints/fields/orders), a `pagelist` field
`sections/payment` → its fields are part of [`fields/order`](/reference/blueprints/fields/order) now

Where you extend one of them, change the name and move it from `sections:` to `fields:`. Under `sections:`, Kirby shows an error in its place.

> [!IMPORTANT]
> If you replaced one of them with a file of your own, such as `/site/blueprints/sections/orders.yml`, move it to `/site/blueprints/fields/` and turn it into a field: `type: fields` becomes `type: group`, `type: pages` becomes `type: pagelist` and `headline` becomes `label`. A file left in `sections/` is ignored without an error.

[`fields/price`](/reference/blueprints/fields/price) is a `prices` field now, with one price per [pricing rule](/guide/configuration/prices). Delete a `/site/blueprints/fields/price.yml` of your own: it replaces the one of Merx without a warning. Prices stored as a plain number keep working.

[`layouts/order`](/reference/blueprints/layouts/order) also has a Personal data tab now. It shows [`fields/personal-data`](/reference/blueprints/fields/personal-data), and that is where your customer fields go — see [Validate checkout](/guide/getting-started/validate-checkout). Merx stores only the fields of the order blueprint: a field your checkout form sends that your blueprint lacks is dropped. Kirby’s [Sections become fields](https://getkirby.com/releases/6/blueprints#sections-become-fields) covers your other blueprints.

## The success page

Merx 1 created a virtual success page and sent the customer there. There is none in Merx 2.

The provider returns the customer to [`/api/shop/success`](/reference/api/routes/shop-success-get), which completes the payment, writes the order page and redirects to it. Delete the `successPage` option and the template that went with it.

A [custom gateway](/guide/payment-gateways/custom-payment-gateway) that handed `url(option('ww.merx.successPage'))` to its provider hands over [`Merx::returnUrl()`](/reference/classes/merx/return-url) now.

## Error messages

Three translation keys were renamed along with the methods.

`error.merx.initializePayment` → [`error.merx.initializeOrder`](/reference/options/translations/error-merx-initializeorder)
`error.merx.completePayment` → [`error.merx.createOrder`](/reference/options/translations/error-merx-createorder)
`error.merx.noPaymentMethod` → [`error.merx.noPaymentGateway`](/reference/options/translations/error-merx-nopaymentgateway)

If you overrode any of them, the [translations reference](/reference/options/translations) lists every string Merx ships today.

## Payment methods and gateways

Payment methods `credit-card-sca`, `credit-card`, `sepa-debit`, `klarna` and `ideal` are removed in favor of `stripe`. You can still use all payment methods mentioned and many more with [Stripe](/guide/payment-gateways/stripe).

The checkout form field that selects one is `payment_gateway`, not `paymentMethod`.

`invoice` is no longer on by default. Switch it on with `'invoice' => true` in the [`gateways`](/reference/options/config-options/gateways) option, see [Invoice](/guide/payment-gateways/invoice).
