Title: Security

----

Headline: Securing order pages

----

Intro: Order pages hold your customers’ personal data. These are the measures to take so that it stays private.

----

Text:

An order page has no login. Whoever knows its URL can read it, so everything on this page is about keeping that URL, and the files behind it, private.

## What Merx does for you

- **Random URLs.** An order page gets a random 16-character id, not its order number, so its URL cannot be guessed from another one.
- **No index of orders.** [`$site->index()`](https://getkirby.com/docs/reference/objects/cms/site/index) contains no order pages, unless the logged-in user may list orders. The `list` option of the order blueprint decides, the same as in the Panel, and by default only admins may. A sitemap or a [`$site->search()`](https://getkirby.com/docs/reference/objects/cms/site/search) built on it leaves them out. An order has no [siblings](https://getkirby.com/docs/reference/objects/cms/page/siblings) either, so `prev()` and `next()` in an order template never lead to somebody else’s order.
- **Security headers.** [`OrderPage::render()`](/reference/classes/order-page/render) sends `Cache-Control: private, no-store`, `Referrer-Policy: same-origin` and `X-Robots-Tag: noindex, nofollow`. Order pages are never written to Kirby’s page cache.
- **A log of every view.** Each time an order page is rendered, Merx logs the order, the Panel user if there is one, and a hash of the visitor’s IP address. It follows the [`logging`](/reference/options/config-options/logging) option, and log files are deleted after a year.
- **Orders that stay as they are.** In the Panel nobody can delete, duplicate or move an order, or change its URL or status.
- **Only admins list orders.** Other roles don’t see the orders in the Panel, in its search or in the orders tab of a product. They can still open an order whose Panel URL they know. Let more roles list orders in your own blueprint:

```yaml title="/site/blueprints/pages/order.yml"
extends: wagnerwagner.merx.pages/order

options:
  list:
    editor: true
```

Only add roles with Panel access. A role for customer accounts would get every order, too.
- **No leftovers.** An [order draft](/guide/glossary) of a checkout that was never completed is deleted by the next checkout once it is a week old.

> [!WARNING]
> Most of this lives in the order blueprint and in the `OrderPage` model. Don’t replace them, extend them: start your own `/site/blueprints/pages/order.yml` with [`extends: wagnerwagner.merx.pages/order`](/reference/blueprints/pages/order), and let your own `/site/models/order.php` extend [`OrderPage`](/reference/classes/order-page). A blueprint written from scratch has none of the `options` that keep an order from being deleted or renamed in the Panel.

## Check it in the Panel

Admins find a *Merx* entry in the Panel menu. It shows the installed version, whether Merx runs in production or test mode, the Stripe and PayPal keys in use with their last four characters, Merx’ options with a note where one differs from its default, for example a changed `ordersPage` that your robots.txt has to name, and these checks:

- which roles can see the list of all orders,
- that visitors can’t list them, which fails when the order or orders page doesn’t use Merx’ model, and that no role without Panel access can,
- test mode on a public server, Stripe test keys in production, and a missing [webhook signing secret](/guide/configuration/stripe-webhooks),
- from your browser, as a visitor: that your robots.txt disallows the orders and that your sitemap.xml lists no orders.

## What is left to you

- Escape everything a customer entered with [`$field->escape()`](https://getkirby.com/docs/reference/templates/field-methods/escape). Merx stores it as it was typed.
- Never list orders in a template. `children()` and `drafts()` of the orders page, and with them `$site->grandChildren()`, still return every order, with its URL: Kirby needs them to find the order of a request. `$site->index()` and `$site->search()` don’t.
- Do not show personal information when it is not necessary.
- Add a robots meta tag to your order template. It tells search engines the same as the header, also when a proxy drops the header.
`<meta name="robots" content="noindex, nofollow">`
- Add a robots.txt to disallow order pages. Your `/orders/` path depends on the [`ordersPage`](/reference/options/config-options/orders-page) option.

```text title="robots.txt"
User-agent: *
Disallow: /orders/
```

- Keep the files private. Orders are text files in your content folder, and the log names every order that was looked at. Make sure neither folder can be requested from the web, and keep both out of a Git repository. Ignoring the orders folder also keeps `.merx-orders.lock` out of it, a file Merx keeps next to the orders so that two of them never get the same number.

```gitignore title="/.gitignore"
/content/orders
/site/logs
```

- Treat an order link like the order itself. It is in the confirmation email, in the customer’s browser history and in your backups.
- Keep your Stripe and PayPal keys in a file that is [not part of your repository](/guide/configuration/stripe-paypal-secrets).

## Further considerations

- Unpublish order pages after a while, as [suggested by @Philip](https://forum.getkirby.com/t/merx-plugin-to-create-online-shops-with-kirby-3/13735/131). The link in an old email stops working then.
- Limit how often an address may request order pages, in your web server or firewall, to stop somebody from trying URLs.
- Send links that are valid once or only for a short time, instead of the URL of the order page.
